# The Skin

Everything a `scene2d.ui` widget is made of. This is the local equivalent of a stylesheet, and the
comparison stops there: nothing here scales, nothing here is a proportion, and there is no cascade.
A button is 60 x 12 px because [`04-hud-layout.md`](04-hud-layout.md) says a column is 106 px wide
and a word of `font-mini` is six pixels a letter.

## What ships

Three files under [`skin/`](skin/), all generated by
[`skin/build-skin.py`](skin/build-skin.py):

| File | What it is |
|---|---|
| `skin.png` | 128 x 19, one atlas page, every drawable |
| `skin.atlas` | the region index, including the nine-patch splits |
| `skin.json` | the Skin, in the form `Skin(FileHandle, TextureAtlas)` reads |

```
python docs/design/skin/build-skin.py
```

It also writes `specimen.png`, which is the widgets stretched to the sizes they ship at and set with
real text. That file is not committed and is not an asset: it exists because a nine-patch that looks
right in the atlas and wrong at 60 x 12 is the normal outcome, and there is no way to know without
stretching it.

## The fonts are not in this atlas

`skin.json` names `font-mini` and `font-title`, and the loader is expected to have put both into the
Skin before reading it:

```java
skin.add("font-mini", miniFont);
skin.add("font-title", titleFont);
skin.load(Gdx.files.internal("skin.json"));
```

They stay out on purpose. The HUD draws text and no widgets, so a font that only existed inside a
widget atlas would have to be loaded twice. [`03-typography.md`](03-typography.md) has the sheet
format.

## The drawables

| Region | Size | Split | Used by |
|---|---|---|---|
| `white` | 1x1 | — | tints, dividers, anything solid |
| `panel` | 11x11 | 3,3,3,3 | dialog and menu backgrounds |
| `plate` | 11x11 | 3,3,3,3 | the two HUD plates |
| `button-up` | 13x13 | 5,5,5,5 | resting button |
| `button-over` | 13x13 | 5,5,5,5 | focused or hovered |
| `button-down` | 13x13 | 5,5,5,5 | pressed |
| `button-disabled` | 13x13 | 5,5,5,5 | unavailable |
| `bar-back` | 7x7 | 2,2,2,2 | progress and slider track |
| `bar-fill` | 5x5 | 2,2,2,2 | boss bar, sliders — W4 |
| `bar-fill-low` | 5x5 | 2,2,2,2 | boss bar below its threshold — W3 |
| `check-off` | 9x9 | — | checkbox, empty |
| `check-on` | 9x9 | — | checkbox, ticked, C1 |
| `cursor` | 5x7 | — | the selection chevron, W4 |
| `focus` | 5x5 | 2,2,2,2 | the four-corner keyboard focus mark, W4 |

**The bevel is the whole visual language.** Every box is N0 outline, one lit row at the top, one
shaded row at the bottom, flat inside; a state is a different pair of ramp steps and nothing else.
Up is N3 lit N4, over is N4 lit N5, down is N2 lit N1 — the light comes from above until the button
is pressed, and then it does not. That is the only affordance available at 12 px and it is enough.

**Disabled is the darkest and the only one that changes the text**, to N3. A greyed-out label at
this size has to lose contrast rather than saturation, because there is no saturation left to lose.

## Colours

All background-legal, because a menu is scenery as far as [`01-palette.md`](01-palette.md) is
concerned and nothing in it may compete with a bullet. The two exceptions are W4 and W3, on the
selection cursor, the focus mark and the bar fill, and both are already fixed by
[`03-typography.md`](03-typography.md)'s table for the selected entry. No widget ever enters hues
320-350; the reserved band belongs to enemy fire even on a screen with no enemies on it, because the
player should never learn that magenta sometimes means "menu".

| Skin colour | ls32 | Where |
|---|---|---|
| `label` | N4 | field names |
| `value` | N7 | values, button text |
| `disabled` | N3 | unavailable entries |
| `selected` | W4 | the entry under the cursor |
| `warning` | W3 | destructive confirmations |

## Keyboard focus is drawn, not implied

`focus` is a nine-patch of four W4 corners with a hollow middle, drawn over the focused widget. It
exists because the game is playable on a keyboard and a pad, and `button-over` alone cannot carry
focus on a pad: there is no pointer to hover with, and a focused-but-not-pressed button that looks
identical to a hovered one leaves the player guessing which entry Enter will take.

## What this page does not decide

Layout. Which widgets a screen has, where they sit and in what order they take focus belongs to
`game-presentation` and to [`04-hud-layout.md`](04-hud-layout.md). This page decides only what a
widget looks like once it is placed.
